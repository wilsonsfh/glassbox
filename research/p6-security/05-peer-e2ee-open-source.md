## 1. Signal libsignal

**Provides.** [X3DH](https://signal.org/docs/specifications/x3dh/) is asynchronous authenticated key agreement using identity keys, a signed prekey, ephemeral DH and an optional one-time prekey. [PQXDH](https://signal.org/docs/specifications/pqxdh/) adds a post-quantum KEM contribution: its stated post-quantum forward-secrecy property is distinct from authentication, which in that revision still relies on discrete-log hardness. The [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/) evolves message keys and mixes fresh DH contributions; symmetric rekeying alone cannot provide its break-in recovery. The current specification is revision 4, dated 2025-11-04, and also describes sparse post-quantum and hybrid Triple Ratchet constructions. These are not properties Glassbox acquires by borrowing a label.

**Identity verification.** Signal's [safety-number design](https://signal.org/blog/safety-number-updates/) presents one per-conversation value, historically 12 groups of five decimal digits, plus a QR representation. Its [current support guidance](https://support.signal.org/hc/en-us/articles/360007060632-What-is-a-safety-number) says verified-number changes require manual approval before a new send and that the number itself does not verify a person's identity. The identifying trust comes from the comparison channel. The old design also accidentally put identifiers into QR codes; the published correction is a useful warning against hiding invite secrets or personal identifiers inside a verification QR.

**What services see.** libsignal itself is a cryptographic library, not a relay. In X3DH/PQXDH the key service sees public identity/prekey bundles and queued initial ciphertext. Routing infrastructure necessarily has destination information and can observe connection IPs, timing and size. [Sealed sender](https://signal.org/blog/sealed-sender/) is a separate envelope mechanism intended to reduce sender disclosure; the publication explicitly distinguishes that from IP/timing correlation. This is not a claim about every current Signal server log or retention setting.

**Published analysis.** The [USENIX Security 2024 PQXDH analysis](https://www.usenix.org/conference/usenixsecurity24/presentation/bhargavan) found specification pitfalls involving KEM binding and other details, while stating they were not exploitable in Signal because of implementation choices. [Fiedler and Günther's analysis](https://eprint.iacr.org/2024/702) also explains KEM binding and domain separation. These are scoped protocol analyses, not an audit of Glassbox, malicious JS delivery or every libsignal dependency. X3DH itself warns that replay without a one-time prekey requires a post-handshake protocol to randomize the responder's encryption key.

**Browser/reuse limit.** The [libsignal README](https://raw.githubusercontent.com/signalapp/libsignal/main/README.md) says use outside Signal is unsupported and APIs can change. Its TypeScript product uses native **Node add-ons** shipped for desktop operating systems, not a documented browser/WASM distribution. Copy the per-session comparison, local verified status, changed-key send block and explicit deletion assumptions. Do not import asynchronous prekey/account/multi-device machinery or promise Signal-equivalent recovery for a synchronous two-browser prototype.

## 2. Matrix vodozemac / Olm / Megolm and SAS

**Provides.** The current [Olm API documentation](https://docs.rs/vodozemac/latest/vodozemac/olm/index.html) describes **3DH** using Curve25519 sender, ephemeral/one-time or fallback keys to initialize a pairwise Double Ratchet; Ed25519 supplies the stable signing fingerprint, not the DH operation. [Megolm](https://docs.rs/vodozemac/latest/vodozemac/megolm/index.html) instead gives each sending participant a group session, whose ratchet state is shared with recipients, normally using Olm for device-to-device key distribution. The [Matrix implementation guide](https://matrix.org/docs/matrix-concepts/end-to-end-encryption/) requires checking sender/recipient/key context and tracking Megolm message indices against replay. It is dated 2023 and still contains libolm-style API examples; it must not substitute for today's vodozemac API.

**Identity verification.** The [v1.19 SAS specification](https://spec.matrix.org/v1.19/client-server-api/#short-authentication-string-sas-verification) is a protocol, not seven decorative emoji. It uses fresh Curve25519 DH, a commitment binding the ephemeral public key to the canonical start event, negotiated algorithms, contextual HKDF, human comparison, then MACs of the actual verified keys and complete key-ID list. It aborts on mismatched commitments, wrong sequencing or comparison failure. Seven emoji encode 42 bits; the decimal alternative encodes three 13-bit groups. The spec requires a non-impersonable out-of-band comparison channel, not necessarily a secret one. Cross-signing adds persistent user/device trust, unnecessary for Glassbox.

**What services see.** Homeservers receive public device keys/prekeys, user/device identities, room IDs, membership and routing events, and ciphertext size/timing; federated participating servers can receive room traffic and relevant state. Encryption of message bodies does not hide the room social graph. Correct key validation is essential against a malicious homeserver: authenticated decryption is not sufficient to establish a human-readable sender label.

**Audit and current weaknesses.** The [30 March 2022 Least Authority report](https://matrix.org/media/Least%20Authority%20-%20Matrix%20vodozemac%20Final%20Audit%20Report.pdf) reviewed particular Rust commits, expressly excluded JavaScript bindings/dependencies and higher-level application interactions, and treated the underlying Olm/Megolm design as out of scope. It recorded resolved input-validation/zeroization issues, but unresolved swap/side-channel exposure and legacy 64-bit MAC truncation. Those historical statuses are not an assertion that every current configuration still has the same defect. Do not repeat the README's “no significant findings” as blanket assurance.

The current advisories add concrete reasons to pin and review versions: [Olm HKDF outputs left in freed memory](https://github.com/matrix-org/vodozemac/security/advisories/GHSA-v27v-f96q-qhjq), [dependency-feature zeroization regressions](https://github.com/matrix-org/vodozemac/security/advisories/GHSA-mxcm-mrw6-c446), and [malformed Base64 Ed25519 keys causing a panic](https://github.com/matrix-org/vodozemac/security/advisories/GHSA-pqp6-f7wc-6498), all fixed in **0.11.2** in November 2026. The memory-read adversary in the first two can include crash-dump/swap access, not merely the relay.

**Browser/reuse limit.** vodozemac is Rust, with a documented browser path through Matrix's crypto WASM bindings, not a drop-in plain-JS two-person room protocol. Copy replay/context discipline and verification state transitions. A later reviewed adapter could use Olm or SAS. Do not use Megolm just because the room has two users: Matrix's persistent history/group-session trade-offs and broad key-distribution surface are mismatched to this ephemeral product. Retained ratchet state can preserve access to historical messages; a symmetric group ratchet does not recover from a stolen current session key without replacement key material.

## 3. Magic Wormhole

**Provides.** The [official overview](https://magic-wormhole.readthedocs.io/en/latest/welcome.html) uses a **SPAKE2 PAKE** with a one-use human code, a WebSocket mailbox/rendezvous server for setup and small encrypted messages, and direct transit or an encrypted transit relay for bulk traffic. The usual code's numeric nameplate is routing information; the default two secret words supply 16 bits of entropy. PAKE prevents passive transcript-based offline password testing; it does not turn a short code into an unguessable bearer secret.

**Identity verification.** Code possession authenticates pairing, not a named person. The [client protocol](https://magic-wormhole.readthedocs.io/en/latest/client-protocol.html) confirms shared-key possession by authenticated encrypted version messages and closes on failed decryption. The [API's optional verifier](https://magic-wormhole.readthedocs.io/en/latest/api.html) is a hash of the established session key, meant for independent comparison. Crucially, requesting it does not pause the protocol: the application must withhold outgoing data and queue/ignore incoming data until users approve the comparison. This directly supports Glassbox's send gate.

**What services see.** The mailbox receives routing/app identifiers, client sides, PAKE messages and phase-labelled ciphertext, with connection IPs and sizes/times. Transit relay operators see connections and encrypted records; direct peers learn network addressing. Default operation is not anonymity. Content protection assumes the code was not stolen and the endpoints execute the intended implementation.

**Published weaknesses.** [Known Vulnerabilities](https://magic-wormhole.readthedocs.io/en/latest/attacks.html) explicitly describes an active interception attempt's one-in-65,536 default-code guessing chance, reliable impersonation if the code is leaked, and mailbox denial of service. Do not reuse a code after failure or let a malicious relay silently trigger repeated client attempts. Honest-server rate limits alone cannot constrain an adversarial server; client abort/retry policy matters. The same document warns that deriving a public routing ID from short secret words gives an offline guessing oracle.

There are also recent **receiver-side**, not PAKE, flaws: [GHSA-4g4c-mfqg-pj8r](https://github.com/magic-wormhole/magic-wormhole/security/advisories/GHSA-4g4c-mfqg-pj8r) allowed a malicious authenticated sender to overwrite local files in 0.21.0–0.22.0, fixed in 0.23.0; [GHSA-cf92-gfcw-6v53](https://github.com/magic-wormhole/magic-wormhole/security/advisories/GHSA-cf92-gfcw-6v53) covers an existing-output-directory traversal case in 0.23.0, fixed in 0.24.0. Encryption does not make the recipient's parsing/file handling trustworthy. No comprehensive independent audit of the current complete Wormhole implementation was established in this bounded research.

**Browser/reuse limit.** The cited implementation is Python 3.10+, not browser executable. The project's [ecosystem page](https://magic-wormhole.readthedocs.io/en/latest/ecosystem.html), explicitly describing April 2025 knowledge, lists Winden and wormhole.page as WASM web clients; browser protocol operation is therefore documented, but those ports were not tested or endorsed here. Copy one-use pairing, code-error handling, independent verifier gating and separation of rendezvous from transit. Do not adopt a two-word code now, direct Python dependencies, or file-transfer features.

## 4. Briar — selected Tor-based P2P comparator

**Provides.** [Briar's architecture/threat model](https://briarproject.org/how-it-works/) synchronizes directly between devices via Tor online, with Bluetooth/Wi-Fi alternatives and optional Briar Mailbox for users online at different times. It explicitly treats compromised devices as attacker-controlled. The current [BHP 0.1 specification](https://code.briarproject.org/briar/briar-spec/-/blob/master/protocols/BHP.md) uses X25519 ephemeral–ephemeral and both static–ephemeral DH contributions, labelled BLAKE2b key derivation, role-specific ownership proofs and an abort if the required minor version is absent. It assumes previously exchanged long-term public keys.

**Identity verification.** Nearby [BQP v4](https://code.briarproject.org/briar/briar-spec/-/blob/master/protocols/BQP.md) scans visible QR commitments to ephemeral public keys, checks the subsequently exchanged keys and confirms a shared secret. Its screen-to-person link is the authentication channel. Remote contact addition in the [user manual](https://briarproject.org/manual/) exchanges `briar://` public-key links. BHP explicitly cannot detect substitution that already happened during that exchange; publicly known links are not secret invitations.

**What services see.** There is no central message-routing server holding everyone's contact graph in the main architecture. Tor infrastructure sees encrypted traffic and adjacent-hop information; a guard can see the connecting user's IP and timing, while Tor onion-service peers do not ordinarily obtain each other's network IP through that route. Contacts and optional mailbox devices remain observers, local wireless traffic has a different exposure boundary, and Tor does not establish protection against arbitrary global timing correlation or compromised endpoints. Glassbox's ordinary WSS/TURN relay sees both connections and their association: it does not inherit Briar's metadata properties.

**Published weaknesses/audits.** The [2017 Cure53 report](https://cure53.de/pentest-report_briar.pdf) found endpoint issues and a DNS leak in RSS importing, illustrating why all ancillary traffic must obey the same route policy. In its [2023 disclosure](https://www.briarproject.org/news/2023-three-security-issues-found-and-fixed/), Briar acknowledged oversized-message crashes, non-canonical encoding enabling duplicate signed messages, and a BHP forward-secrecy design flaw fixed in **1.5.3**; it stated Tor's extra encryption prevented exploitation of the last issue in its deployment.

The [Radically Open Security report, final 4 March 2024](https://www.opentech.fund/wp-content/uploads/2024/06/report_briar-android.pdf), reviewed Android/Desktop/protocols, confirmed the revised DH construction addressed the handshake flaw, and documented overlay, low-entropy Wi-Fi app-sharing PSK and local-service risks. Its remote-verification finding recommended a later independent verification path; do not assume Tor replaces identity verification. The findings are scoped to the reviewed versions, not a current universal status claim.

**Browser/reuse limit.** Briar is a native Android/Desktop product with bundled Tor and local transport integration, not a browser-native SDK. Copy observer-specific metadata disclosure, canonical encoding, mandatory downgrade rejection and the clear compromised-device boundary. Do not import its native stack, long-term contacts, offline synchronization or claim Tor-equivalent metadata resistance from ordinary P2P/WebRTC.

## 5. Element Web — selected browser-native comparator

**Why this one.** Element has an actual web client, a current supported-browser policy, documented web WASM bindings, a formal Matrix verification specification, an official verification guide and actionable public client advisories. It is deliberately the **integration/UX** comparator; comparator 2 covered the underlying cryptographic components. No claim of superiority over other messengers is needed to justify this evidence-rich choice.

**Provides and verifies.** Element inherits Matrix's Olm key agreement and Megolm room encryption rather than inventing another handshake. The [WASM README](https://github.com/matrix-org/matrix-sdk-crypto-wasm) describes a no-network-I/O `OlmMachine`, web `initAsync`, separate web/Node entry points and an in-memory store when no IndexedDB store is supplied. The [official user guide](https://static.element.io/pdfs/element-user-guide.pdf) tells users to compare the same ordered emoji in person or over video, with explicit match/mismatch actions. The [current device guide](https://docs.element.io/latest/element-support/device-verification/how-to-verify-devices/) distinguishes verifying one's own new session from recovery and says the blanket exclusion rollout date for unverified devices is postponed. Do not infer that all current Element conversations are automatically blocked pending cross-user verification.

**What services/endpoints see.** Homeserver observations are the Matrix metadata listed above, not plaintext message bodies when the protocol and client behave correctly. The web hosting origin is an additional adversary: it delivers executable JS/WASM that can access plaintext/keys. E2EE does not stop a malicious origin replacing that code. The guide's history backups and the WASM README's recommendation to use IndexedDB address persistent messaging needs, not Glassbox's no-history objective; do not copy persistence or optional trace logging from the example.

**Published weaknesses.** The [2024 history-key disclosure](https://www.matrix.org/blog/2024/10/security-disclosure-matrix-js-sdk-and-matrix-react-sdk/) affected legacy non-Rust key forwarding to newly invited unverified users/devices; Rust crypto did not implement that vulnerable feature. [CVE-2025-48937](https://github.com/matrix-org/matrix-rust-sdk/security/advisories/GHSA-x958-rvg6-956w) let a malicious homeserver relabel a decrypted room event's sender because the trusted session check omitted the sender; [Element Web 1.11.103](https://github.com/element-hq/element-web/releases/tag/v1.11.103) shipped its fix. The separate [June 2026 to-device sender-binding advisory](https://github.com/matrix-org/matrix-rust-sdk/security/advisories/GHSA-wfq4-36m3-9g42) affected crypto versions >=0.12.0 and <0.16.1 and needed homeserver collusion/control. The [WASM changelog](https://github.com/matrix-org/matrix-sdk-crypto-wasm/blob/main/CHANGELOG.md) records that fix in v18.3.0 and a later v19.0.1 update to vodozemac 0.11.2. These illustrate application identity-binding failures even with a reviewed cryptographic library; the 2022 vodozemac audit does not cover this entire browser product.

**Browser/reuse limit.** The [Element README](https://github.com/element-hq/element-web) supports the last two major desktop Chrome/Firefox/Edge and last two Safari versions, with mobile web community support. Browser usability is established by documentation, not an interoperability test in this task. Copy explicit verification states and inspect its architecture/tests. A full Matrix account, room-state, cross-signing, backup and key-forwarding system is unnecessary scope and leak surface for Glassbox.

## Bootstrap decision for Glassbox's fragment invite

**Keep a high-entropy PSK Noise bootstrap now, conditionally on R6's implementation/vector/browser gates.** Glassbox generates 32 random bytes, not a password. [Noise §9](https://noiseprotocol.org/noise.html#pre-shared-symmetric-keys) specifies a 32-byte PSK and mixes it into keys and handshake hash; its rationale explicitly discourages low-entropy passwords. PAKE's principal additional benefit—preventing offline guessing of low-entropy credentials—does not materially improve an already random invitation against a malicious relay that lacks it. A PAKE adds another protocol/library/integration surface without fixing invite theft, malicious web delivery or device compromise. This is a protocol-selection judgment, not validation of the proposed Noise/secretstream composition.

For `NNpsk0`, do not send chat in the first handshake flight: its PSK protection precedes the final ephemeral DH contribution. Require fresh ephemeral keys, canonical role/version/room binding and mutual final-key confirmation before any plaintext reaches the conversation. Later PSK disclosure is distinct from disclosure of completed session keys; statements about earlier ciphertext depend on fresh DH and deletion, including the limitations of JS/WASM memory clearing.

**If short spoken codes become a requirement, choose a reviewed balanced PAKE instead of hashing the code into a PSK.** [SPAKE2 RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html) specifies peer password exchange plus mandatory confirmation, group validation, fresh randomness and contextual binding; Wormhole demonstrates one concrete variant, not automatically byte-for-byte RFC compatibility. [CPace draft -21](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-cpace-21) targets balanced peer pairing and one active guess per interaction; its [25 November status evidence](https://datatracker.ietf.org/doc/draft-irtf-cfrg-cpace/history/) shows it in RFC Editor processing, not yet a published RFC. Select based on reviewed implementation and browser evidence, not novelty. [OPAQUE RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html) is an augmented client/server protocol with password registration and credential records: that persistent-account problem is not this peer invitation problem. Do not place an OPAQUE “password server” between chat endpoints merely to claim PAKE.

A short-code mode also needs client-enforced one-attempt failure, fresh-code restart, expiry, user-visible failures and abuse limits. Do **not** derive the publicly visible room ID by hashing a low-entropy code; that creates a separate offline oracle despite using PAKE. A random public locator and secret code have different jobs. Keep the current high-entropy invite mode and any future short-code mode explicitly labelled; never silently downgrade.

## What independent fingerprint comparison adds

With an unexposed random invite, a correct PSK handshake already rejects relay key substitution. With an invite thief, it only proves **someone** knows the bearer credential. The thief can race the intended participant, replace the peer or mount two authenticated sessions. Independent comparison binds the actual session to the person recognized through the external channel and exposes those different sessions. Wormhole's verifier demonstrates this extra check even after PAKE succeeded.

The comparison channel needs authenticity and independence from the attacked path, not secrecy. Comparing inside the same unverified chat, or through the same compromised invitation-sharing account, adds no independent identity evidence. A thief who can also impersonate the person on the comparison channel defeats both checks. A malicious origin/extension can lie about the fingerprint and steal plaintext; no honest-looking comparison badge remedies that. Recipient copying/screenshots remain outside protocol control.

The compared value must cover the **completed session**, not just the room ID or invite secret. Use the final Noise handshake hash as the channel-binding input with a fixed versioned fingerprint derivation/encoding; it already incorporates the handshake/prologue binding. A 256-bit displayed fingerprint may be a domain-separated SHA-256 encoding of that input, but its precise encoding needs a test vector. Changing keys, protocol/room context or beginning a new session must clear local comparison status.

## UI and acceptance tests to borrow

Display one common **session code**, with the full 256-bit value in grouped hex and a machine-comparable versioned QR for the prototype; do not copy Signal's decimal derivation while claiming it is the same algorithm. A reversible full-value decimal presentation can be added later if localization matters. QR contents must omit the invitation secret and personal identifiers. Prefer scanning in person; copying the full verification value is explicit and can itself leave clipboard/history metadata.

Use states **“Invite authenticated”**, **“Not compared”**, **“Compared on this device”**, **“Session changed — compare again”** and **“Comparison failed”**. The first means bearer-secret possession, not identity. Match and mismatch are distinct actions; mismatch aborts, key change disables sends, and reload/reconnect creates a new comparison requirement. Do not advertise a remotely attested human comparison.

SAS words/emoji belong **later**, only with a reviewed interactive commitment/MAC verification protocol or a separately reviewed transcript-bound construction. Matrix's seven emoji with textual descriptions and decimal fallback are documented options; select the same negotiated representation on both devices. Wormhole's two secret words are **pairing credentials**, not a post-handshake SAS. Never turn the first few hex digits into friendly words and assume Matrix's one-attempt property: unconstrained attackers can search truncated comparisons. Abort duplicate concurrent verification attempts and enforce a timeout; usability tests must include keyboard, screen-reader and cross-language comparisons.

Three comparator-driven tests should fail before a “compared conversation” can be accepted: (1) an invite-holding relay creates two sessions and relabels the sender/room/role—independent full comparison differs and unbound labels must never be trusted; (2) the relay replays, reorders, cross-room reflects or non-canonically re-encodes authenticated material—reject before DOM display without advancing trusted state; (3) a compared peer reconnects with fresh session keys during a queued send—clear comparison and block both queued and new sends. A future SAS mode also needs deliberate commitment mismatch, negotiated-method mismatch and no-MAC-completion tests. These are proposed tests, not tests executed in R5.
