# R2 — Cloudflare open-source skills, MCP servers and code

Evidence checked on **25 November 2026**. Scope: Glassbox’s two-person, ephemeral browser chat; a ciphertext-only Worker/Durable Object relay; optional native WebRTC/TURN; no accounts, model access to chats, or content storage. This review read public documentation, repository READMEs, selected source files, licences and repository metadata. It did not install, clone, execute upstream code, authenticate to Cloudflare or deploy anything.

`command -v client-mcp-cli` found no executable. The existing Client utilities directory also contained no `client-mcp-cli`. Read-only MCP server discovery listed only `client-tools` and `exa`, **not Cloudflare**. No connector was created, enabled or authorized, and no Cloudflare account tool was called. This is a session snapshot, not a claim that Client lacks Cloudflare integrations generally.

The [recommended API MCP](https://github.com/cloudflare/mcp) needs Cloudflare OAuth authorization with selected permissions, or a scoped API bearer token. Both user and account tokens are supported; account-token auto-detection additionally needs `Account Resources : Read`. An operational integration should grant only the necessary read permissions and constrain approved endpoints/accounts; general `execute` capability is not intrinsically read-only. The precise Client catalogue entry’s login flow and effective scopes were **not exercised**.

The [standalone documentation MCP](https://github.com/cloudflare/mcp-server-cloudflare/tree/main/apps/docs-ai-search) explicitly requires **neither authentication nor OAuth**, at `https://docs.mcp.cloudflare.com/mcp`. It is not configured here. Public docs can already be retrieved over HTTP without enabling a connector. Only non-sensitive documentation questions belong in a docs MCP: its implementation sends searches to Cloudflare AI Search, not an offline local index.

## 3. Skills are instructions, not servers or cryptographic controls

[Docs for agents](https://developers.cloudflare.com/docs-for-agents/) is a **documentation page and delivery convention**, not a separately established repository. It links to `cloudflare/skills`, Markdown pages (`/index.md` or `Accept: text/markdown`), product-scoped `llms.txt`, and MCP servers. The exact GitHub URLs `cloudflare/agent-skills` and `cloudflare/docs-for-agents` returned **404**. This does not establish that no differently named repository exists; the verified canonical skills repository is `cloudflare/skills`.

Each skill is an on-demand `SKILL.md` with instructions/references. It is not executable enforcement, not an endpoint protection agent and not an encryption library. Relevant selections are `cloudflare`, `durable-objects`, `workers-best-practices`, `wrangler` and `turnstile-spin`. The current plugin bundles the broad `cloudflare` API MCP, not just the public docs server; installing the plugin is therefore not the same operation as copying selected instruction files. No installation was performed here.

Two concrete conflicts require a **project-specific override before reuse**:

- The [Durable Objects skill](https://raw.githubusercontent.com/cloudflare/skills/main/skills/durable-objects/SKILL.md) correctly routes to current APIs, one coordination object per room and runtime tests, but says “persist first, cache second” and recommends SQLite. For Glassbox this must mean, at most, expiry/tombstone metadata—not chat, invites, keys, SDP, ICE or Wire Receipt captures. Its generic persistence example is inappropriate for the transcript.
- The [Workers best-practices skill](https://raw.githubusercontent.com/cloudflare/skills/main/skills/workers-best-practices/SKILL.md) recommends enabling Workers Logs **and traces**. Blindly applying that default increases intermediate-service and metadata retention. Glassbox must prohibit payload/URL/secret logging and third-party analytics/error content, explicitly select any minimal operational telemetry, and test the logging boundary. The skill usefully flags hardcoded secrets, weak randomness, unbounded buffering and module-level mutable request state, but cannot enforce the override itself.

These instructions reduce implementation drift and accidental leak paths when converted into review rules and tests. They cannot stop a malicious origin delivering replacement JavaScript, a privileged extension, a compromised device or a recipient copying plaintext.

## 4. MCP catalogue: useful development access, not chat protection

The [official catalogue](https://developers.cloudflare.com/agents/model-context-protocol/cloudflare/servers-for-cloudflare/) and [repository README](https://github.com/cloudflare/mcp-server-cloudflare) distinguish broad API access from typed product tools. Current endpoints use **`/mcp`**; the repository says retired `/sse` endpoints return `410 Gone`. Stateless protocol handling does **not** imply zero retained OAuth state, diagnostics, product logs or application caches.

The recommended MCP uses Dynamic Workers/Code Mode to discover and call APIs without putting thousands of schemas in the model context. That is a development-efficiency technique, **not an E2EE protocol**. No skill or MCP changes what a TLS-terminating CDN can see: without application encryption it sees chat content; with correctly implemented application E2EE it sees application ciphertext plus routing/network metadata. MCP access could expose whatever the application mistakenly logged.

Current [Workers testing docs](https://developers.cloudflare.com/workers/testing/vitest-integration/) recommend **`@cloudflare/vitest-plugin`**, running locally with Miniflare and isolated per-test-file storage; they provide migration from older `@cloudflare/vitest-pool-workers`. Pin a compatible release set, not current main: the inspected Miniflare manifest is a beta. Tests of relay behavior should accompany independent browser crypto tests owned by R6, not substitute for them.

Meet’s README formats safety numbers with Crockford base32 and defaults to 20 characters (100 bits), configurable from 16–52. That is a useful usability reference, **not a reason to shorten Glassbox’s proposed full 256-bit comparison without an analysis of the verification protocol**.

For OHTTP, [RFC 9458 §6–7](https://www.rfc-editor.org/rfc/rfc9458.html) requires separate relay and gateway operators for the stated privacy goal: relay learns the client network identity but not the encapsulated HTTP content; gateway learns decrypted HTTP content but not the original client IP. Both legs require HTTPS; identifying forwarded headers, unique configurations, contents and correlation can defeat unlinkability. A Cloudflare relay plus Cloudflare-operated gateway does not meet the independent-operator assumption. OHTTP encrypts to the **gateway**, not the other chat participant; the proposed application E2EE would still be necessary. Its request/response abstraction is not a drop-in persistent WebSocket/DataChannel transport.

## 6. Unverified items and decisions still needed

No browser build, crypto-vector run, package install, upstream test or production operational check was performed in R2. CIRCL Go→Wasm feasibility and Meet’s MLS interoperability were not validated. The initial Python HTTPS reader failed desktop CA validation; TLS-validating curl succeeded without disabling certificate checks. Later GitHub API HTTP 403s were worked around using public HTML/Atom feeds, not credentials. Exact `realtimekit`/`agent-skills`/`docs-for-agents` URLs returned 404; core RealtimeKit OSS availability remains unverified.

Before code reuse, resolve the precise Realtime example files’ licences. Before operational MCP access, determine the intended account, effective read scopes and allowed endpoints, with separate authorization. Before any relay observability is enabled, define the exact retained fields/retention and prove the absence of invite, key, message, SDP and ICE content in synthetic tests. None of these development tools proves authentic browser delivery, endpoint integrity, recipient deletion or absence of infrastructure retention.
