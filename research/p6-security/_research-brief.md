## The product we are building (Problem 6, working name Glassbox)
Original task text: "P2P encrypted chat room. Users can connect and exchange messages, with the focus on preventing chat data from leaking as much as possible. Accounts/login are optional and not the focus. A server may be used for discovery, signaling or relay, but think about how chat data could leak on the sending side, in transit, through intermediate services and on the receiving side, and how to reduce those risks. HTTPS/WSS alone is not end-to-end encryption. Do not claim the product is absolutely secure; explain the actual security boundaries in a verifiable way."

Existing design (proposal, not built): two-person ephemeral browser chat, no accounts, memory-only bounded transcript, random invite secret in the URL fragment, authenticated key agreement then AEAD records, full-fingerprint comparison through an independent channel, a relay that only sees ciphertext plus metadata, optional WebRTC data channel with signaling encrypted over the control stream, an attack lab (tamper, replay, reorder, wrong room, key substitution) and an opt-in Wire Receipt of what the relay actually saw. Read analysis/p6-p2p-encrypted-chat.md for the full design and caveats.

Do not install any vendor endpoint agent, do not create accounts, do not call vendor APIs with credentials, do not enable TLS interception, do not upload chats or keys anywhere, do not deploy anything to Cloudflare. 2. No marketing claims. Separate three things for every finding: (a) what the vendor or project actually provides, (b) what it can do for a browser E2EE chat prototype, (c) what it cannot do. Say explicitly when a product is irrelevant. Do not pad.
3. Honesty rule: never write that anything makes the product "secure", "unhackable" or "audited". A control reduces a named risk against a named adversary. Name both.
4. Record licence, last commit date, stars, and whether the code is maintained for every open-source repo you cite. Prefer primary sources (vendor docs, RFCs, repo README, source code).
5. Output: a Markdown report at the exact path given in your section, with cited URLs, plus a JSON result with the schema required by the caller. Keep the report under 250 lines, evidence first, no executive summary, no bullet padding. End with a table "Adopt now / Adopt later / Skip" where every row names the risk it reduces, the adversary, the effort and the exact limit.
6. Time box: aim for 12 to 20 minutes. Stop when the evidence needed for the table is in hand.

Risk vocabulary to use: sender endpoint (clipboard, screenshot, extension, malicious JS delivery, XSS, logs, history, URL fragment leakage), transit (TLS terminating middlebox, DLP TLS inspection, proxies, captive portals), intermediate services (relay, signalling, TURN, CDN, WAF logs, analytics, error tracking, DNS), receiver endpoint (copy, screenshot, notifications, backups, swap, crash dumps), key and identity (MITM key substitution, invite leakage, weak verification, replay, reorder, downgrade), metadata (IP, timing, size, room id, who talks to whom).
